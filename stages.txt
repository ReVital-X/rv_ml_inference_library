You are currently at the **Bare-Metal Proof of Concept (PoC)** stage.

You have successfully built the underlying "physics engine" of your library. You proved that pure integer fixed-point math works, you handled the requantization bottleneck, and you verified that the RISC-V silicon can boot and execute the logic without an operating system.

However, to make this a library that other developers on GitHub will actually want to use, you need to transition from "a collection of math functions" to a **Formal C API**.

Since your goal is to provide a developer experience similar to PyTorch or TensorFlow Lite Micro, here is the exact roadmap from your current PoC to a production-ready open-source repository.

### Stage 1: The Proof of Concept (Completed)

* **Achieved:** Matrix multiplication loops, ReLU, Argmax, integer requantization, bare-metal linker scripts, QEMU execution, and a basic Makefile.
* **Status:** The math is mathematically sound and hardware-compatible.

### Stage 2: Struct Abstraction (Your Immediate Next Step)

Right now, your `dense_layer_forward` function takes 8 different variables. If a user wants to build a 5-layer network, passing 40 variables around manually is chaotic and prone to bugs.

To mimic PyTorch, you must hide the raw arrays inside C `struct` definitions.

* **The Tensor Struct:** Instead of passing a raw `int8_t*` pointer and its `size`, you create a `Tensor` struct that holds the memory pointer and its shape (dimensions).
* **The Layer Struct:** You create a `LinearLayer` struct that permanently bundles the weights, biases, multiplier, and shift values together.
* **The Constraint:** Because you are avoiding heap allocation (`malloc`), these structs must be designed so the user can allocate them entirely on the stack or in `.bss` using `static`.

### Stage 3: The Build and Verification Pipeline

Other developers need guarantees that your math doesn't break when they use it on different architectures (like Arm64/NEON, which you plan to support).

* **CMake Migration:** As discussed, you will swap the handwritten `Makefile` for a `CMakeLists.txt` file so anyone can build it on Windows, Linux, or macOS.
* **Unit Testing:** You will integrate a C testing framework (like Unity or CMocka) to run automated tests. You will feed a tensor into your C code, feed the exact same tensor into PyTorch, and assert that the outputs match perfectly.
* **CI/CD Automation:** You can set up GitHub Actions (similar to your Jenkins pipelines) to automatically compile the RISC-V binary and run the unit tests every time you push new code.

### Stage 4: The Python Export Toolkit

A C library is useless if users cannot get their PyTorch weights into it.

* You need to package your Python export script into a clean module (e.g., `export_to_c.py`).
* It should accept a PyTorch `nn.Module`, automatically calculate the quantization scales, extract the weights, and generate the `weights.h` file for the user.

### Stage 5: Adding More Inferences

Once the `Tensor` and `Layer` API structure from Stage 2 is locked in, adding new ML models becomes modular.

* To add Computer Vision models (like ResNet), you will write a `conv2d_forward` function and a `Conv2DLayer` struct.
* To add sequence processing, you write an `rnn_forward` function.
* Because everything uses the same `Tensor` input/output format, users can easily chain your new CNN layers with your existing Dense layers.
